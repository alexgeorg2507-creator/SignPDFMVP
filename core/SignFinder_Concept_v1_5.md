## 1. Резюме концепции

SignFinder — продукт для автоматизации **процесса подписания договоров**, а не их юридического анализа. Ниша на mid-tier рынке практически пустая: коммерческие contract review системы (Kira, Luminance, LawGeex, Harvey AI) фокусируются на анализе уже подписанных документов, а движки подписания (DocuSign, Adobe Sign) делают разметку мест подписи вручную. SignFinder автоматизирует именно тот шаг, который остальные оставляют человеку — определение **где, кому и в каком порядке** ставить подпись.

**Целевая аудитория:** delivery-менеджеры, юристы среднего звена, sales-операционисты, бухгалтеры — все, кто обрабатывает 10-200 договоров в месяц без enterprise-CLM системы.

**Ключевая метрика успеха:** доля документов, прошедших полный цикл «загрузил → автоматически нашлись места → подписано → скачано» без ручных правок. Цель MVP — 70%, продакшен — 90%+.

**Экономическая модель решения:** многоуровневая обработка с оптимизацией стоимости токенов.

| Уровень | Метод | Стоимость | Доля документов (цель) |
|---------|-------|-----------|------------------------|
| 1 | Regex по шаблонам (parties.json) | ~$0 (только compute) | 50% |
| 2 | LLM-валидация regex-кандидатов | $0.01-0.02 | 30% |
| 3 | LLM-first поиск (fallback) | $0.05-0.10 | 15% |
| 4 | Ручная разметка с сохранением шаблона | трудозатраты оператора, амортизация на повторных | 5% |

## 3. Сравнение с аналогами на рынке

### 3.1 Прямые конкуренты (контролируемая разметка мест подписи)

| Продукт | Класс | Что делает | Чего нет |
|---------|-------|------------|----------|
| **DocuSign** | E-signature platform | Ручное перетаскивание полей подписи на PDF | Авто-поиск мест подписи — слабый, по якорным тегам типа `\sign_here\\` |
| **Adobe Sign** | E-signature platform | То же, шаблоны полей | Авто-разметка только если документ создан в Adobe экосистеме |
| **HelloSign / Dropbox Sign** | E-signature platform | API + ручная разметка | Нет интеллектуального поиска мест |
| **PandaDoc** | Document automation | Создание + подписание шаблонов | Авто-поиск только в собственных шаблонах |

**Вывод:** Все они — движки подписания. Автоматизация поиска мест подписи в **чужих** загружаемых документах у них слабая или отсутствует.

### 3.2 Косвенные конкуренты (contract review / extraction)

| Продукт | Класс | Сильные стороны | Слабые стороны | Цена |
|---------|-------|-----------------|----------------|------|
| **Kira Systems (Litera)** | Contract review | 1000+ типов пунктов, обученные ML-модели на корпусах юр.данных | Корпоратив, сложная интеграция, английский приоритет | enterprise |
| **Luminance** | Contract review | Pattern recognition + ML, due diligence | Закрытая модель, vendor lock | enterprise |
| **LawGeex** | Contract review | Бинарное review vs корпоративных политик («accept/reject» по пунктам) | Не делает разметку для подписания | mid-enterprise |
| **Ironclad CLM** | Full-stack CLM | Жизненный цикл договора, workflow, репозиторий | Громоздкий, дорогой, перестройка процессов | enterprise |
| **Harvey AI** | LLM-копилот для юристов | GPT-4 на бэке, заточен под выводы, редактирование | Не работает с подписанием как процессом | enterprise |
| **Spellbook (Word add-in)** | LLM-копилот | Прямо в MS Word, GPT-base | Только англоязычные документы, не PDF | mid |

**Вывод:** Все системы работают с **уже подписанными** документами для анализа рисков или с пустыми шаблонами для генерации. Никто не автоматизирует процесс «найти где подписать в чужом договоре».

### 4.2 Облачные сервисы парсинга и извлечения (опции для v2.0+)

#### 4.2.1 Google Document AI

Полноценная платформа для парсинга документов от GCP. Состоит из нескольких процессоров:

| Процессор | Что умеет | Применимость к SignFinder |
|-----------|-----------|----------------------------|
| **Document OCR** | OCR любых документов, включая сканы | Закрывает кейс сканированных договоров |
| **Form Parser** | Извлечение пар «label: value» из форм | Малоприменимо для свободных договоров |
| **Layout Parser** | Разбор структуры документа (заголовки, абзацы, таблицы, иерархия) | **Очень полезно для v1.4.1 и v2.0** — структура разделов из коробки |
| **Contract Parser (specialized)** | Готовый процессор для договоров: извлекает стороны, даты, суммы, термины, обязательства | **Прямая альтернатива части LLM-логики extraction в v2.0** |
| **Custom Extractor** | Обучение на своих документах для специфических полей | На v2.0 не нужно, на v3.0+ возможно |

**Контракт-парсер — ключевая фича для v2.0:**
- Из коробки извлекает: стороны (parties), даты (effective_date, expiration_date), суммы, термины, юрисдикцию
- Возвращает структурированный JSON с координатами на странице
- Обучен на корпусе договоров на разных языках, включая русский (с оговорками на качество)

**Стоимость (на момент mid-2026):**
- Document OCR: ~$1.50 за 1000 страниц
- Layout Parser: ~$10 за 1000 страниц
- Contract Parser: ~$30 за 1000 страниц
- В сравнении: один LLM-вызов Claude Sonnet 4.6 на документ ~$0.01-0.05

**Применение в SignFinder:**
- **v1.4.1 → v1.4.2:** опциональное использование Layout Parser для определения структуры разделов вместо эвристик. Параллельный путь рядом с локальной эвристикой.
- **v2.0:** Contract Parser как первичный extractor сторон в pre-flight check. Если справился — LLM не нужен для шага 1 «extraction». Если нет — fallback на Claude.
- **v2.0+:** Document OCR для сканированных договоров. Открывает новый класс документов.

**Vendor lock-аргументация для MVP:**
- Уже на GCP — Cloud Run, GCS. Document AI — той же экосистемы. Зависимость не увеличивается.
- На уровне MVP vendor lock некритичен — отвязка позднее через абстракцию `DocumentExtractor` интерфейса.
- Главный риск — стоимость роста объёма. На 1000 договоров в месяц через Contract Parser: ~$30, что некритично.

#### 4.2.2 AWS Textract

Конкурент Document AI от Amazon. Сильные стороны другие.

| Что умеет | Применимость к SignFinder |
|-----------|----------------------------|
| **DetectDocumentText** | Базовый OCR + текст | Аналог Document OCR Google |
| **AnalyzeDocument (TABLES)** | Извлечение таблиц с разметкой ячеек | **Сильнее Google в табличных кейсах** |
| **AnalyzeDocument (FORMS)** | Пары label-value | Аналог Form Parser Google |
| **AnalyzeDocument (LAYOUT)** | Разбор структуры (с 2023) | Аналог Layout Parser Google |
| **AnalyzeDocument (SIGNATURES)** | **Детекция мест подписи на странице** | **Прямо релевантно к v2.0 R-04 — детекция уже наложенных подписей**, если изменим скоуп |
| **Queries** | Кастомные «извлеки X из документа» через natural language | Альтернатива LLM-вопросов |

**Стоимость:**
- DetectDocumentText: ~$1.50 за 1000 страниц
- AnalyzeDocument (TABLES/FORMS/LAYOUT): ~$15-30 за 1000 страниц
- Queries: ~$15 за 1000 страниц + плата за каждый вопрос

**Применение к SignFinder:**
- Сильнее всех в таблицах. Полезно для COR-003 из corrections.md («подпись внутри ячейки таблицы»).
- Уникальная фича — детекция подписей (SIGNATURES feature). Если когда-то изменим решение и захотим проверять «вторая сторона уже подписала» — Textract это закрывает.
- Минус для нас — мы на GCP. Переезд частично в AWS добавляет cross-cloud сложности (IAM, биллинг, latency).

**Vendor lock-аргументация для MVP:**
- Технически возможно вызывать AWS из Cloud Run. Гранулярная авторизация через access key или Workload Identity Federation.
- Стоимость cross-cloud трафика на маленьких объёмах несущественна.
- На MVP — не оправдано добавлять AWS-зависимость, если Document AI справляется. Резерв на случай явно лучших табличных кейсов.

#### 4.2.3 Azure Form Recognizer (Document Intelligence)

Прямой конкурент обоим, от Microsoft.

| Что умеет | Применимость к SignFinder |
|-----------|----------------------------|
| **Read model** | OCR + базовая структура | Аналог Document OCR |
| **Layout model** | Структура + таблицы | Аналог Google Layout / AWS Layout |
| **General Document** | Универсальный extractor пар «ключ-значение» | Для нас неинтересно |
| **Custom models** | Обучение на своих документах | Аналог Custom Extractor Google |
| **Prebuilt: Contract model** | Специализированный процессор для договоров | **Прямой аналог Contract Parser Google** |

**Стоимость:**
- Read model: ~$1.50 за 1000 страниц
- Layout model: ~$10 за 1000 страниц
- Custom models: дороже, инвестиция в обучение
- Prebuilt Contract: аналогично Google ~$25-50 за 1000 страниц

**Применение к SignFinder:**
- В мейнстриме для тех, кто на Azure. Технически сопоставим с Document AI.
- На GCP — нет смысла, увеличиваем cloud-фрагментацию без выгоды.

#### 4.2.4 Итоговое сравнение облачных решений

| Параметр | Google Document AI | AWS Textract | Azure Form Recognizer |
|----------|---------------------|-------------|------------------------|

| Силён в структуре | **Лучший** (Layout Parser) | Хорошо | Хорошо |

| Поддержка польского | Хорошая | Хорошая | Хорошая |
| Vendor lock для GCP-стека | Минимальный | Cross-cloud | Cross-cloud |

**Рекомендация для MVP:** на этапе v1.4-v2.0 — Google Document AI как основной облачный extractor, при необходимости. AWS Textract в резерве для специфичных кейсов (таблицы, детекция подписей).

## 5. Архитектура многоуровневой обработки

### 5.1 Идеология: каждому документу свой уровень

Цель — минимизировать стоимость обработки за счёт раннего возврата на простых кейсах.

```
┌─────────────────────────────────────────────────────────────┐
│  Документ загружен                                          │
└─────────────────────────────────────────────────────────────┘
                          ↓
            ┌─────────────────────────────┐
            │ Уровень 0: Шаблон документа │  ← новое в v1.4.3
            │ Fingerprint совпал >0.85?   │
            └─────────────┬───────────────┘
                          │ нет        │ да → применить сохранённый шаблон
                          ↓            │
            ┌─────────────────────────────┐
```

## 6. Процесс «Анализ договора» — детализация Уровня 2

Эта глава раскрывает Уровень 2 архитектуры обработки. Уровень 2 ранее в концепции назывался коротко «LLM-fallback» — это упрощение оказалось неточным. На практике речь идёт о полноценном многоступенчатом процессе с промежуточными артефактами, которые используются не только для поиска мест подписи, но и для дальнейших версий продукта (pre-flight check v2.0, шаблоны документов).

### 6.1 Терминология

Для дальнейшего обсуждения нужно зафиксировать понятия.

| Термин | Определение | Где живёт |
|--------|-------------|-----------|
| **Синоним стороны** | То, как сторона названа в шапке конкретного договора. Три типа: юрлицо (ООО Ромашка), роль (Арендатор, Исполнитель), ФИО подписанта (Иванов И.И.). Все три типа — синонимы одной стороны. | В сессии Streamlit на время обработки документа. Опционально сохраняется в `parties.json`. |
| **Маркер места подписи** | Универсальный признак «здесь подписывают»: символы подчёркивания (`___`), М.П., Место подписи, Подпись, штамп, и аналоги на других языках (Czytelny podpis, Signature). Не зависит от конкретного договора, зависит только от языка. | Опции проекта (`markers.json` или раздел в общем конфиге). Стабильная константа продукта. |
| **Сторона** | Обобщённое понятие подписывающей стороны: «Арендатор», «Исполнитель», «Заказчик». В рамках конкретного договора имеет набор синонимов. В реестре сторон агрегирует паттерны для повторного использования. | `parties.json` в GCS — накопительный реестр. |
| **Адаптивный regex** | Регулярное выражение, сгенерированное LLM специально под конкретный договор на основе его синонимов и универсальных маркеров. Совместим с форматом `parties.json`. | В сессии Streamlit. Опционально сохраняется в `parties.json`. |
| **Шапка договора** | Первая страница содержательного текста договора с упоминанием сторон, реквизитов, подписантов (преамбула). НЕ путать с титульным листом — если первая физическая страница содержит только название документа без сторон и реквизитов, шапкой считается следующая страница с фактическим началом договорного текста. Единственное место в договоре, где синонимы вводятся явно. | Извлекается через PyMuPDF на лету, с детекцией титульного листа (см. 6.4.1). |

**Детекция титульного листа:** считаем страницу титульной если на ней <300 символов значимого текста ИЛИ нет ни одного из ключевых маркеров преамбулы («именуем», «в лице», «настоящ», «заключил», "hereinafter", "represented by", "between", "umow", "zawart"). Если первая страница — титульная, шапкой считается вторая (или первая с маркерами).

**Важное ограничение:** синонимы вводятся в договоре только в шапке. Сокращения и аббревиатуры посреди документа («Исп.» вместо «Исполнитель», «Р-р» вместо «Арендатор») — нарушение стандарта оформления и в общем случае не поддерживаются. Документы с такими сокращениями уходят в Уровень 3 (ручная разметка).

### 6.2 Постановка процесса

**Цель процесса:** дать пользователю инструмент адаптивного поиска мест подписи в договорах, которые не покрываются Уровнем 1 (Regex по реестру) — либо потому что сторона новая, либо потому что формулировки нестандартные.

**Принципиальное отличие от существующего обучения** (`pattern_extractor.py` на странице «Обучение системы»):

| Параметр | Обучение (v1.3) | Анализ договора (v1.4+) |
|----------|-----------------|-------------------------|
| Цель | Создать паттерны для класса документов | Найти места в одном конкретном договоре |
| Где живёт результат | Сохраняется в `parties.json` для будущих документов | По умолчанию в сессии, опционально в `parties.json` |
| Промежуточные артефакты | Скрытые внутри пайплайна | Видимые пользователю, контролируемые |
| Кто запускает | Администратор для подготовки реестра | Любой оператор для текущего документа |
| Частота вызова | Редко (раз на новый тип договора) | По мере необходимости на любом документе |

Эти два процесса разделяют общую инфраструктуру (LLM, страгическая нарезка контекста, формат паттернов), но решают разные задачи.

### 6.3 Архитектурное решение: пайплайн против монолита

При проектировании рассматривались два варианта.

**Вариант А: монолитный LLM-вызов.** Один большой промпт получает PDF и подписанта, возвращает координаты мест подписи. Декомпозиция задачи — внутри LLM, для пользователя процесс непрозрачен.

**Вариант Б: многоступенчатый пайплайн.** Несколько последовательных LLM-вызовов с явными промежуточными артефактами: сначала синонимы из шапки, потом regex-паттерны под этот договор, затем применение паттернов.

**Сравнение:**

| Параметр | Монолит | Пайплайн |
|----------|---------|----------|
| Архитектурная простота | Выше | Ниже |
| Стоимость токенов | Ниже (~$0.05 за документ) | Выше (~$0.07 за документ) |
| Скорость отклика | Один round-trip к LLM (5-10 сек) | 2-3 round-trip (10-20 сек) |
| Прозрачность для пользователя | Низкая (чёрный ящик) | Высокая (видны синонимы, regex) |
| Реюз промежуточных данных | Невозможен | Синонимы используются в v2.0 pre-flight check |
| Отладка при ошибках | Сложная | Простая (видно на каком шаге сломалось) |
| Контроль качества пользователем | Только финальный результат | На каждом шаге |

**Выбор:** пайплайн. Аргументация — синонимы из шапки являются ценным артефактом сами по себе и переиспользуются в v2.0 для правила R-03 (соответствие маркера у места подписи синониму стороны). Дополнительная стоимость в $0.02 на документ компенсируется отладочной прозрачностью и контролем качества.

### 6.4.1 Детекция титульного листа

Многие договоры (особенно корпоративные) начинаются с титульного листа — отдельной страницы с названием документа, логотипом, иногда датой и номером, но БЕЗ упоминания сторон и преамбулы. Если по ошибке подать титульный лист в шаг 1 пайплайна, LLM не найдёт никаких сторон и пайплайн остановится с непонятной для пользователя ошибкой.

**Алгоритм определения шапки:**

```python
def find_header_page(doc) -> int:
    """Возвращает индекс страницы с реальной преамбулой договора."""
    
    PREAMBLE_MARKERS = {
        "ru": ["именуем", "в лице", "настоящ", "заключил", "с одной стороны"],
        "en": ["hereinafter", "represented by", "between", "agreed as follows"],
        "pl": ["umow", "zawart", "reprezentowan", "zwan"]
    }
    
    MIN_MEANINGFUL_CHARS = 300
    
    for page_idx in range(min(3, doc.page_count)):  # проверяем первые 3 страницы
        text = doc[page_idx].get_text().strip()
        
        # Слишком мало текста = вероятно титульник
        if len(text) < MIN_MEANINGFUL_CHARS:
            continue
        
        # Есть маркеры преамбулы = это шапка
        text_lower = text.lower()
        markers = PREAMBLE_MARKERS.get(language, PREAMBLE_MARKERS["ru"])
        if any(marker in text_lower for marker in markers):
            return page_idx
    
    # Fallback — первая страница с достаточным объёмом текста
    for page_idx in range(min(3, doc.page_count)):
        if len(doc[page_idx].get_text().strip()) >= MIN_MEANINGFUL_CHARS:
            return page_idx
    
    return 0  # совсем ничего не нашли — берём первую
```

**Где используется:** на шаге 1 пайплайна «Анализ договора», на шаге 3 pipelineAuto1 (детект синонимов нашей стороны), и в fingerprint computation для прототипа «Светофор на потоке» (SimHash вычисляется от шапки, не от титульника).

**Параметризация:** маркеры преамбулы по языкам хранятся в `markers.json` рядом с маркерами подписи. Это вторая секция того же конфига — связанные сущности, оба зависят от языка.

### 6.5 Хранение данных процесса

### 6.6 Место в общей картине

Процесс «Анализ договора» — это третий путь обработки документа, не замена существующих путей.

| Путь | Когда применим | Откуда берёт паттерны | Доля документов |
|------|---------------|----------------------|------------------|
| **Уровень 1 — Regex по реестру** (режим «По роли» в v1.3) | Сторона есть в `parties.json`, паттерны работают | Заранее накопленный `parties.json` | 99% по оценке тестов v1.3 |
| **Уровень 2 — Анализ договора** (новое в v1.4) | Сторона новая или нестандартные формулировки в шапке | Генерирует под конкретный договор, опц. сохраняет в `parties.json` | Хвост непокрытых документов |
| **Уровень 3 — Ручная разметка** (v1.4.3) | Документ-исключение, нет текстовых якорей или сокращения в шапке нарушают стандарт | Координаты от клика, сохраняются как DocumentTemplate | Редкие случаи |

«Сферический конь в вакууме» из непокрытых документов разводится либо в Уровень 2 (если шапка стандартная, но реестр ещё не знает эту сторону), либо в Уровень 3 (если шапка нестандартная или скан без текстового слоя). Это и есть закрытие 100% документов.

### 6.9.1 Ретенция шаблонов — автоматическая чистка хранилища (v1.5+)

**Проблема:** на этапе тестов реестр (`parties.json` и `templates/`) растёт без ограничений. Каждый прогон pipelineAuto1 создаёт новую запись. За месяц-два реестр засоряется устаревшими, дублирующимися и одноразовыми шаблонами, что замедляет matching и затрудняет администрирование.

**Решение:** автоматический механизм ретенции по статистике использования, активируется в v1.5+.

**Политика ретенции (стартовая, настраиваемая в опциях):**

| Условие | Действие | Период проверки |
|---------|----------|------------------|
| Шаблон не применялся 30+ дней | Перевод в статус `archived` (исключение из активного matching, но без удаления) | Ежедневно по cron |
| Шаблон в `archived` 90+ дней | Удаление с бэкапом в `templates/_archive/` | Еженедельно |
| `times_rejected / times_applied > 0.5` за последний месяц | Пометка `low_quality`, ручной разбор оператора | Еженедельно |
| Дубликат: header_simhash совпадает > 0.95 с существующим шаблоном | Объединение `usage_stats`, удаление младшего | При создании нового шаблона |

**Что хранится в `usage_stats` (расширение структуры DocumentTemplate из раздела 7.4):**

```json
"usage_stats": {
  "times_applied": 5,
  "times_confirmed": 4,
  "times_rejected": 1,
  "last_used": "2026-05-15T10:00:00Z",
  "created_at": "2026-03-01T12:00:00Z",
  "status": "active | archived | low_quality | deleted"
}
```

**Реализация:**
- Cron-задача через Cloud Scheduler (бесплатно для редких запусков)
- Скрипт `core/template_retention.py` — проходит по реестру, применяет политику, логирует действия
- Лог ретенции в `logs/retention.jsonl` для аудита
- Возможность ручной отмены через UI «Реестр шаблонов» (восстановление из архива)

**Что НЕ делаем:**
- Не удаляем шаблоны без бэкапа — всегда сохраняем в `_archive/` минимум 90 дней
- Не делаем агрессивную чистку (< 30 дней) — пользователь может работать сезонно
- Не делаем ML-предсказание полезности шаблона — простые правила лучше для предсказуемости поведения

**Связь с прототипом «Светофор на потоке»:** прототип уже накапливает `usage_stats`, но политика ретенции не применяется. После калибровки на данных прототипа политика активируется в v1.6.

## 7. Светофор и реестр шаблонов — детализация Уровня 0

Эта глава раскрывает Уровень 0 архитектуры обработки и одновременно описывает целевую операционную модель продукта — переход от утилиты «один документ → одно подписание» к конвейеру обработки потока документов.

### 7.1 Светофор как операционная модель

**Девиз системы:** «сомневаешься — спроси».

Каждый документ при обработке получает один из двух статусов:

| Статус | Что значит | Что делает система |
|--------|-----------|---------------------|
| 🟢 **Зелёный** | Система уверена в результате (score ≥ 0.95) | Автоматически применяет шаблон, подписывает, кладёт в архив подписанных |
| 🟡 **Жёлтый** | Любое сомнение, коллизия двух шаблонов, неоднозначная классификация, ошибка пайплайна | Помечает «требуется оператор», даёт оператору посмотреть и решить |

**Бинарность только для UI.** Внутри система считает полный score 0.0-1.0 и логирует все детали для аналитики и калибровки порогов. На уровне действий — два состояния, и это правильно: при любом сомнении документ безопаснее отправить оператору, чем подписать неверно.

**Целевая операционная модель (v2.0+):** документы поступают потоком (bulk-загрузка, email, API), система автоматически рассортировывает на «зелёные → подписаны» и «жёлтые → требуется оператор», оператор разбирает только жёлтые. На MVP/v1.5-1.6 — бинарный светофор как индикатор уверенности при синхронной обработке одного документа.

### 7.2 Что такое «почти такой же договор»

Уточнённое понимание после обсуждений с пользователем:

«Тот же договор» — это документ, у которого **с вероятностью 99.9% места подписи находятся там же**, и с вероятностью 99.5% совпадает количество страниц и распределение слов по страницам. По сути — тот же шаблон от того же контрагента, отличающийся только реквизитами (адреса, суммы, даты, номера) и, возможно, мелкими правками формулировок.

Это **класс 2** по шкале схожести: тот же шаблон, мелкие правки. Большинство договоров одной организации (≈99%) попадают именно сюда — это типовые шаблоны, размноженные на множество контрагентов.

**Различение классов:**

| Класс | Похожесть | Описание | Стратегия | Где применимо |
|-------|-----------|----------|-----------|---------------|
| 1 | 95-100% | Тот же шаблон, другие реквизиты | Применить шаблон, светофор 🟢 | Большая часть документов одной организации |
| 2 | 80-95% | Тот же шаблон, мелкие правки (новый раздел, перестановка пунктов) | Применить шаблон, светофор 🟡 (для проверки) | Эволюция шаблонов во времени |
| 3 | 50-80% | Тот же тип договора, разные шаблоны разных контрагентов | Не применять, светофор 🟡, regex из реестра отработает базовый поиск | Разные контрагенты с похожими типами договоров |
| 4 | <50% | Принципиально разные документы | Не предлагать ничего, светофор 🟡, идти стандартным пайплайном | Новые типы документов |

Класс 3 в большинстве случаев закрывается обычным regex из `parties.json` — паттерны structural, переживают замену шапки. Поэтому fingerprint-matching критичен именно для класса 1 (идеальное узнавание) и класса 2 (узнавание с предупреждением).

### 7.3 Как измерять похожесть

Базовый принцип — **многомерное сравнение по нескольким сигнатурам**, каждая ловит свою грань похожести. CRC32/SHA не годятся: малейшее изменение даёт полностью другой хеш.

**Каскадная стратегия (от дешёвой к дорогой):**

```
1. Быстрая отсечка (мгновенно)
   - page_count в пределах ±2
   - total_chars в пределах ±20%
   - language совпадает
   → Отсекает 95% несовпадений за миллисекунды

2. SimHash шапки (дёшево)
   - SimHash шапки документа (страница с реальной преамбулой,
     определяется через find_header_page() — см. раздел 6.4.1)
   - Порог: similarity > 0.85
   → Различает контрагентов лучше всего

3. Сравнение структуры разделов (дёшево)
   - Jaccard similarity по списку заголовков разделов
   - Порог: ≥ 0.8

4. Композитный score (только для прошедших 1-3)
   - Взвешенная сумма всех сигнатур
   - Веса настраиваемые в config

5. Embeddings (только при коллизии двух кандидатов с близкими score)
   - Семантическое сходство шапки
   - На v1.6 не реализуем, резерв на v2.0+
```

**Кандидаты в сигнатуры:**

| Сигнатура | Что ловит | Стоимость | Стабильность к правкам |
|-----------|-----------|-----------|------------------------|
| Количество страниц | Грубая отсечка | мгновенно | Низкая (страница уплыла = другой хеш) |
| Распределение символов по страницам | Структуру документа | мгновенно | Средняя |
| SimHash шапки | Стороны, юрлица, тип договора | дёшево | Высокая для класса 1, средняя для 2-3 |
| Список заголовков разделов | Структуру и порядок частей | дёшево | Высокая |
| Список ключевых юридических фраз | Тип договора | средне | Высокая для класса 3 |
| Embeddings шапки | Семантическое сходство | дороже (LLM-вызов) | Очень высокая |
| Координаты прошлых подписей | «То же место в макете» | бесплатно | Средняя |

**Композитный score для v1.6 (стартовая формула):**

```python
score = 0.4 * simhash_similarity(headers)        # шапка различает контрагентов
      + 0.3 * jaccard(section_titles)            # структура разделов
      + 0.2 * cosine(chars_per_page_normalized)  # распределение объёма
      + 0.1 * (1 - abs(page_count_diff) / max_pages)
```

Веса в `config/scoring_weights.json`, настраиваемые через UI. Калибровка — на накопленных данных прототипа «Светофор на потоке».

### 7.5 Текстовые якоря — единый формат описания мест подписи

В концепции v1.2 шаблон содержал два разных типа источника информации о местах подписи: `regex_patterns` (текстовые паттерны для поиска) и `manual_coordinates` (абсолютные координаты клика). Это дуализм: два механизма в одном шаблоне, две логики применения, две точки отладки.

**В концепции v1.3 шаблон унифицирован** — все места подписи описываются единым типом сущности: **текстовый якорь**. Якорь может быть создан автоматически (из regex-паттерна, обнаруженного pipelineAuto1) или вручную (через клик оператора на странице автоподписания). Логика применения шаблона одинакова для обоих источников.

#### 7.5.1 Принцип якорения

**Фундаментальное правило:** подпись в SignFinder всегда привязана к тексту документа — слову, фразе или линии подчёркиваний. UI не позволяет оператору ставить подпись в пустую область страницы. Это гарантирует:

- Любой шаблон переносим на похожие документы — текст найдётся где угодно, неважно сдвинулась ли страница
- Fingerprint matching не зависит от абсолютных координат
- Все места подписи описываются единым типом сущности
- Прозрачность для пользователя: «подпись стоит здесь потому что в документе есть текст X»

**Если документ не имеет текста рядом с местом подписи** (редкий случай нестандартной вёрстки, например, пустые ячейки таблицы без заголовков) — он обрабатывается через отдельную обходную процедуру, не через шаблонную систему. В реальных мидл-сегмент договорах такие документы практически не встречаются.

#### 7.5.2 Алгоритм клик → текстовый якорь

Четыре уровня от сильного к слабому:

```
Уровень 1 — Точный текст рядом (радиус ~30pt)
  Клик возле "Арендатор:" → якорь «справа от Арендатор:»
  Pattern: Арендатор[\s:]+_{3,}

Уровень 2 — Текст в той же строке (горизонтальная линия)
  Клик в правую часть строки "Заказчик / Исполнитель ___" → якорь «после слова Исполнитель»
  Pattern: Исполнитель[\s_]+_{3,}

Уровень 3 — Текст в области страницы (радиус ~200pt)
  Клик в правый нижний угол, рядом "М.П." → якорь «в области М.П.»
  Pattern: М\.П\.[\s\S]{0,200}_{3,}

Уровень 4 — Линия подчёркиваний
  Клик на линию ___ без текста рядом → якорь «линия подчёркиваний N на странице»
  Pattern: _{5,}

Нет якоря (4 уровня не сработали) → клик не принимается, UI показывает подсказку
```

Алгоритм идёт сверху вниз — выбирает первый подошедший уровень. **Fallback на абсолютные координаты отсутствует** — это принципиально, см. раздел 7.5.1.

#### 7.5.3 Структура якоря

```json
{
  "id": "anchor_001",
  "anchor_type": "text_proximity",
  "anchor_level": 1,
  "anchor_text": "Арендатор",
  "position": "right",
  "offset_pt": 50,
  "generated_pattern": "Арендатор[\\s:]+_{3,}",
  "context_before": "Подпись сторон:",
  "context_after": "Должность:",
  "page_hint": "last",
  "added_by": "manual_click | auto_regex",
  "added_at": "2026-05-20T14:30:00Z",
  "usage_stats": {
    "matched_times": 0,
    "failed_times": 0
  }
}
```

Поле `added_by` различает якорь созданный пользователем кликом и автоматически из regex-паттерна. Логика применения одинаковая, различие только для отладки и аналитики.

Поля `context_before` и `context_after` — для **дезамбигуации**, когда текст-якорь встречается в документе несколько раз. Если слово «Арендатор» в трёх местах — контекст определяет какой именно.

#### 7.5.5 Применение шаблона

Когда пользователь загружает новый документ и шаблон сматчился (v1.8):

1. Каждый якорь из шаблона ищется в новом документе по `generated_pattern` с учётом `context_before`/`context_after`
2. Найденная позиция конвертируется в bbox для наложения подписи
3. Если якорь не найден — он помечается как failed для этого документа, `usage_stats.failed_times++`
4. Если все якоря шаблона найдены — документ полностью покрыт, светофор зелёный
5. Если часть якорей не найдена — светофор жёлтый, оператор разбирается

#### 7.5.6 Граничные случаи

| Кейс | Решение |
|------|---------|
| Оператор кликнул в пустую область | UI не принимает клик, показывает подсказку «клик принимается только над текстом или подчёркиваниями» |
| Якорь-текст встречается в документе несколько раз | Используем `context_before`/`context_after` для дезамбигуации, выбираем ближайший к ожидаемой странице |
| Документ не имеет текста рядом с местом подписи | Out of scope шаблонной системы, обрабатывается через обходную процедуру |
| Алгоритм клик→якорь не построил якорь на 4 уровне | Возврат `None`, UI показывает «не удалось построить якорь, попробуйте ближе к тексту» |
| Якорь сработал на месте где уже стоит auto-подпись от regex | Дедупликация — одна позиция, один якорь |

#### 7.5.7 UX-флоу на странице Авто-подписание (v1.7)

```

2. pipelineAuto1 отработал — найдены места подписи через regex (auto_regex якоря)
3. Превью документа с пагинацией по страницам:
   - Селектор номера страницы [- N +]
   - Чекбоксы найденных мест на текущей странице (over the preview)
   - Рендер страницы с наложенными подписями
4. Под превью — режим:
   [👁 Просмотр] (по умолчанию) — клики игнорируются
   [✏ Добавить место подписи] — режим клика
5. В режиме клика:
   - Mousemove → полупрозрачная рамка размера подписи следует за курсором
   - В пустой области без якоря → рамка красная, клик не принимается
   - Клик в валидной зоне → подпись фиксируется в bbox рамки
   - Drag размещённой подписи → подпись перетаскивается, якорь пересчитывается
```

### 7.6 Explainability — обязательное требование

В юридическом продукте прозрачность матчинга — не UX-плюшка, а **функциональное требование**. Юрист не доверяет чёрному ящику, который сказал «92% похоже, применяю». Каждый матч должен объясняться 2-3 строчками человеческим языком.

**Формат объяснения:**

```
"Шапка договора почти идентична (95%).
 Структура разделов совпадает 9/10 — в новом документе появился раздел 
 'Дополнительные условия'.
 Размер документа совпадает: 12 страниц."
```

Не цифры, не оценки в попугаях — **что именно совпало, что не совпало, и в каком объёме**. Это даёт пользователю основания для решения «доверяю» или «проверю руками».

Объяснение формируется автоматически из `score_breakdown` через шаблонизатор. LLM для этого не нужен — выбор из 5-10 типовых формулировок по результатам сравнения.

### 7.7 Учёт синонимов стороны при матчинге

**Критическое требование:** перед применением шаблона система должна сверять синонимы нашей стороны.

Сценарий: пользователь обучил систему на договоре где «наша сторона = Арендатор». В новом договоре наша сторона = «Исполнитель» (по данным из `signer_profile.json` определена другая сторона). Несмотря на высокий fingerprint score (макет похож, объём похож), **применять шаблон нельзя** — это другая роль для нашей компании.

**Правило:** если синонимы нашей стороны из нового документа (полученные после шага 3 pipelineAuto1) не пересекаются с `source.synonyms_used` шаблона — это **сильный сигнал к жёлтому светофору**, независимо от fingerprint score.

### 7.8 Прототип «Светофор на потоке» — испытательный стенд

**Статус:** architectural spike, не продакт-фича. Цель — собрать данные для калибровки алгоритма перед полноценной реализацией v1.6.

**Зачем нужен прототип:** ответить на три вопроса, на которые сейчас нет данных:

1. Работает ли fingerprint matching на реальных документах
2. Какие пороги светофора правильные (0.95 для зелёного взято с потолка)
3. Какие сигнатуры в fingerprint действительно различают шаблоны, а какие — шум

**Что получаем после 1-2 недель использования:**

- Распределение score — гистограмма реальных значений
- Распределение по корзинам 🟢/🟡 при реальном потоке
- Анализ ошибок — каждый клик пользователя «это другой документ» или «всё правильно» при противоположном светофоре
- Подтверждённый набор fingerprint — какие сигнатуры различают, какие шум
- Готовая база для v1.6 — после калибровки алгоритм просто оборачивается в продакшен-флоу

### 7.12 Хранение шаблонов

| Параметр | Решение |
|----------|---------|
| Где живут | Отдельная коллекция `gs://signfinder-config/templates/` |
| Формат | По одному JSON файлу на шаблон, имя — `{template_id}.json` |
| Индекс | Сводный `templates/_index.json` для быстрого листинга без перебора всех файлов |
| Бэкап | Аналогично `parties.json` — с timestamped копиями при изменении |
| Версионирование | На v1.6 не делаем — каждый шаблон автономный. При сильном изменении создаётся новый |

### 7.13 Что НЕ делаем в прототипе

- Не подписываем автоматом даже зелёные — только показываем что нашли. Подписание добавится в v1.6.
- Не сохраняем PDF на сервер — только в сессии. Реальное хранилище — на v1.7+.
- Не делаем очередь и корзины — все документы в одной таблице, статус = цвет светофора.
- Не делаем уведомления — пользователь видит таблицу и сам разбирается.
- Не делаем сложные сигнатуры (embeddings, key phrases) — только page_count, simhash, section_titles, chars_per_page. Если этого мало — увидим на данных, добавим в v1.6+.
- Не делаем оптимизацию — скорость на 12-50 документах не критична. Performance — потом.
- Не делаем ML-обучение весов на ходу — подбор эмпирический по данным прототипа.

### 7.15 Целевая операционная модель: путь от утилиты к конвейеру

Постановка светофора как операционной модели — это **смена парадигмы продукта** с «утилита для одного документа» на «конвейер обработки потока». Реализуется поэтапно:

| Версия | Что делаем | Что НЕ делаем |
|--------|-----------|---------------|
| v1.5 (текущая) | pipelineAuto1, синхронная обработка одного документа | Не вводим очереди, не сохраняем PDF |
| **Прототип** | Bulk-загрузка, светофор как индикатор, калибровка | Не подписываем автоматом |
| v1.6 | Светофор продакшен, автоподпись для зелёных, ручной разбор жёлтых | Не делаем bulk-загрузку как продакшен-флоу |
| v1.7 | Bulk-загрузка в продакшен, сортировка по корзинам | Документы по-прежнему только в сессии |
| v1.8 | Очередь с персистентным хранением, корзины на Cloud Storage | Не делаем notifications/SSO |
| v2.0 | Async API, push-уведомления, аудит-лог | Не делаем mobile, RBAC |
| v2.x | RBAC, мобильные клиенты, интеграции | — |

Это позиционирование пересматривает главу 1 концепции: продукт движется из mid-market утилиты к mid-to-enterprise конвейеру. Не значит, что MVP-формат отменяется — это значит, что v1.6+ закладывает фундамент для конвейера.

## 8. API-слой — переход от Streamlit-монолита к standalone сервису

Эта глава появилась в концепции v1.4. До v1.8 продукт работал как Streamlit-приложение, где UI и бизнес-логика жили в одном процессе. С v1.9 бизнес-логика выделяется в отдельный сервис `signfinder-api` на FastAPI, Streamlit становится одним из клиентов наряду с мобильным приложением и интеграциями.

### 8.1 Цель и обоснование выделения API

**Цель:** превратить SignFinder из веб-утилиты для одного оператора в платформу, доступную через множество интерфейсов.

**Конкретные потребности, которые покрывает API:**

| Потребность | Без API | С API |
|-------------|---------|-------|
| Мобильное приложение iOS/Android | Невозможно (Streamlit не работает как backend для нативных приложений) | Тонкий клиент через REST |
| Интеграция с почтовым клиентом (IMAP-бот) | Невозможно (нет headless режима) | Бот шлёт PDF на `/v1/analyze`, получает результат |
| MCP-сервер для Claude Desktop / Cursor | Невозможно | MCP-обёртка над REST API за неделю |
| Сторонние интеграции (n8n, Zapier, Make) | Невозможно | Webhooks + REST endpoints |
| Биллинг и квоты | Невозможно | API key → tenant → лимиты |
| Multi-tenant и RBAC | Невозможно | Headers с tenant_id, права через scopes |
| **Desktop on-premise (закрытый периметр клиента)** | Невозможно (Streamlit-deployment специфичен для cloud) | **`signfinder-core` как pip-пакет можно поставить в контейнер у клиента** |

**Бизнес-смысл:** API превращает SignFinder из инструмента для оператора в продукт, который можно встроить в любой workflow клиента и продавать вызов наружу. Это не просто архитектурное упражнение — это переход в другую бизнес-модель.

**Принципиальное архитектурное решение v1.4:** ядро системы выделяется в **отдельный pip-пакет `signfinder-core`**, который:
- Не зависит от FastAPI, Streamlit или какого-либо UI-фреймворка
- Не привязан к GCP — storage abstraction поддерживает локальный filesystem, GCS, S3
- Не требует cloud-инфраструктуры — конфигурация через env vars
- Используется как в Cloud-варианте (через `signfinder-api`), так и в Desktop on-premise варианте (через `signfinder-desktop` — см. главу 10)

Это и есть **single source of truth** для бизнес-логики SignFinder.

### 8.2 Архитектурный выбор: stateless без хранения документов

**Принципиальное решение концепции v1.4:** API не хранит документы между запросами.

**Что это значит:**
- Клиент держит PDF у себя (в памяти мобильного приложения, в очереди интеграции, в `st.session_state` Streamlit)
- Каждый запрос к API передаёт PDF в теле (multipart upload)
- Подписанный PDF возвращается в HTTP response body, на сервере не сохраняется
- На сервере живут только: **шаблоны**, **fingerprint**, **конфигурации**, **PNG подписи**, **аудит-лог**

**Аргументация выбора (stateless vs persistent):**

| Параметр | Stateless | Persistent (с TTL) |
|----------|-----------|---------------------|
| Архитектурная сложность | Минимальная | Высокая (TTL, ретенция, GDPR-вопросы) |
| GDPR-compliance | Чисто (мы не храним персональные данные дольше HTTP-запроса) | Нужны политики хранения, согласия |
| Подходит для мобильного приложения | Да (PDF в памяти приложения) | Да |
| Подходит для интеграций | Да (PDF в буфере интеграции) | Да |
| Подходит для двустороннего подписания (sessions) | Нет, нужен отдельный слой | Да |
| Стоимость инфраструктуры | Минимум | Storage + TTL workers |
| Время реализации v1.9 | Меньше | Больше |

**Решение:** v1.9 — чистый stateless. Если в будущем появится потребность в двусторонних сессиях подписания (контрагент A → отправил по ссылке → контрагент B подписал) — это будет **отдельный опциональный слой sessions** поверх базового API, добавленный в v2.1+ по запросу пользователей.

### 8.3 Базовые сущности и доменная модель

Не «endpoint на каждую кнопку Streamlit», а ресурсы доменной модели:

| Ресурс | Что это | Где живёт |
|--------|---------|-----------|
| **Document** (в payload) | Загруженный PDF/DOCX в теле запроса | У клиента, передаётся в каждом запросе |
| **Template** | DocumentTemplate с fingerprint и якорями | GCS `templates/` |
| **Anchor** | Текстовый якорь, описывающий место подписи | Внутри Template или как утилитный объект |
| **SignerProfile** | Данные подписанта (компания, ФИО, алиасы) | GCS `signer_profile.json` |
| **Party** | Сторона договора с regex-паттернами | GCS `parties.json` |
| **SignatureImage** | PNG подписи оператора | GCS `signature_<signer_id>.png` |
| **ProcessingResult** | Результат обработки документа (светофор, найденные места) | В response body, на сервере не хранится |
| **Job** | Async задача обработки (для bulk и интеграций) | Cloud Tasks + результат в GCS с TTL 7 дней |
| **AuditLog** | Журнал решений системы | Cloud Logging (структурированные JSON) |

### 8.6 Протоколы и принципы

#### REST + JSON + HTTPS

Стандартный выбор. Аргументация против альтернатив:

- **GraphQL:** соблазнительно для мобильных (один запрос вместо пяти), но overkill для MVP. Сложнее кэшировать, мониторить, писать клиенты.
- **gRPC:** невозможно вызвать из браузера, MCP-сервер написать сложнее, нет нативной поддержки в почтовых ботах.
- **WebSocket:** для нашего use case (загрузил → обработал → скачал) двунаправленные каналы не нужны.

#### Авторизация — API key через Secret Manager

```
Header: Authorization: Bearer sk_live_abc123...
```

В v1.9 — один статичный ключ в Secret Manager, single-tenant. В v2.0+ — несколько ключей с правами (admin/read-only/sign-only). Multi-tenant с tenant_id в каждом ключе — после первого Enterprise-клиента.

OAuth2/JWT — отложено до v2.x когда появится UI с пользовательским логином (мобильное приложение в v2.0 использует API key).

#### Pagination — cursor-based

Любой `GET /v1/<resource>` возвращающий список — пагинируется:

```
GET /v1/templates?limit=50&cursor=eyJpZCI6...
```

Cursor-based вместо offset-based — переживает добавление/удаление шаблонов во время пагинации.

#### Async обработка

`POST /v1/analyze` принимает параметр `async`:

- **Sync (default):** ждём результат, возвращаем 200 OK с ProcessingResult. Для мобильного клиента и ручной загрузки.
- **Async:** 202 Accepted с job_id, обработка в фоне через Cloud Tasks. Для bulk и интеграций.

```
POST /v1/analyze?async=true → 202 { "job_id": "..." }
GET  /v1/jobs/{job_id}      → { "status": "completed", "result": {...} }
```

#### Webhooks с HMAC-подписью

Когда внешний сервис хочет реагировать на события:

```
POST /v1/webhooks
{
  "url": "https://customer.example.com/sf-callback",
  "events": ["document.signed", "document.requires_review"],
  "secret": "wh_secret_xyz"
}
```

Webhook отправляется с HMAC-подписью в заголовке для проверки подлинности. Без webhooks интеграции делают polling — это дорого и тупо.

#### Rate limiting

```
HTTP 429 Too Many Requests
Header: Retry-After: 60
```

Лимиты на API key: 60 запросов в минуту, 1000 в час (бесплатный план). Премиум — по биллинговой модели после v2.0.

#### Versioning

URL-based: `/v1/...`, `/v2/...`. Старые версии живут минимум 6 месяцев после анонса новой.

### 8.7 Технологический стек API

| Компонент | Что | Зачем |
|-----------|-----|-------|
| **FastAPI** | Веб-фреймворк | Async, OpenAPI автоматом, типизация через Pydantic |
| **Pydantic v2** | Модели запросов/ответов | Валидация на входе, типизация |
| **Cloud Run** | Хостинг | Отдельный сервис `signfinder-api` рядом с `signfinder-web` |
| **Cloud Storage** | Шаблоны, конфиги, PNG подписей, job results | Существующая инфраструктура |
| **Cloud Tasks** | Очередь async задач | Стандартный GCP-сервис |
| **Cloud Logging** | Структурированные логи, аудит | Бесплатно до 50 ГБ/мес |
| **Secret Manager** | API keys, ANTHROPIC_API_KEY | Не в env vars, безопасно |

**Почему FastAPI, не Flask:**
- Async — критично для LLM-вызовов (секунды ожидания)
- OpenAPI/Swagger из коробки — клиентам сразу видны контракты
- Pydantic — модели данных типизированы
- Современный стандарт, активно развивается

### 8.8 Связь со Streamlit после v1.9

После выделения API Streamlit становится **одним из клиентов**, не монолитом. Все вызовы из Streamlit идут через HTTP к `signfinder-api`:

```
До v1.9:
Streamlit → core/*.py → GCS, Anthropic API

После v1.9:
Streamlit → HTTP → FastAPI (signfinder-api) → core/*.py → GCS, Anthropic API
                ↑
        Mobile, MCP, integrations
```

Streamlit рефакторится:
- Не вызывает core/*.py напрямую
- Не работает с GCS напрямую
- Все операции — через `core/api_client.py` (тонкая HTTP-обёртка)

Это «минимальный рефакторинг», который ты хотел — Streamlit становится тонким клиентом, бизнес-логика жёстко закрыта в API.

### 8.9 Открытые вопросы по API

| Вопрос | Контекст | Решение |
|--------|---------|---------|
| Sessions для двустороннего подписания | Когда контрагент подписывает после нас | Отложено до v2.1+, по запросу пользователей мобильного приложения |
| Multi-tenant и RBAC | Несколько компаний-клиентов на одной инсталляции | После первого Enterprise-клиента, в v2.x |
| OAuth2 для пользовательских сессий | Когда появится UI с логином | v2.x, когда web-фронтенд для пользователей |
| Биллинг и квоты | Платная подписка | Отдельная задача после v2.0 |
| MCP-сервер | Доступ из Claude Desktop, Cursor | Тонкая обёртка над API, делается за неделю после v1.9 |
| Detect already-signed documents | Документ уже подписан второй стороной — что делать? | Отдельная задача после первой обратной связи от пользователей |

## 9. Мобильные клиенты — нативное приложение iOS

**Статус в концепции v1.5:** мобильные клиенты перенесены в **главу 15 «Идеи развития»** — не входят в MVP. Эта глава сохраняется как архитектурный референс для будущей реализации, когда multi-tenant SaaS будет готов и появится бизнес-кейс мобильного приложения.

Глава появилась в концепции v1.4. v2.0 — первая платформа (iOS), v2.2+ — Android по результатам обратной связи.

### 9.1 Выбор платформы: iOS первой

**Обоснование:**

| Параметр | iOS | Android |
|----------|-----|---------|
| Платёжеспособность mid-segment B2B | Выше | Ниже |
| Fragmentation (версии OS, экраны) | Минимум | Высокая |
| App Store моратории и approval | Дольше | Быстрее |
| Стандартизация PDF-работы | Хорошие нативные библиотеки (PDFKit) | Менее зрелые |
| Стоимость разработки на одного пользователя | Выше за квалификацию разработчика | Ниже |

## 10. Desktop on-premise ветка — для корпоративных клиентов с закрытым периметром

**Статус в концепции v1.5:** Desktop on-premise превращается в **v1.11 IMAP-клиент в Docker (single-user)** — становится приоритетом MVP. Раньше эта ветка планировалась как v2.2 после iOS, теперь поднята раньше из-за конкретного корп.клиента. Архитектурные решения этой главы (single-source `signfinder-core`, storage abstraction, контейнерное приложение) остаются актуальными для v1.11.

Эта глава появилась в концепции v1.4. Альтернативная ветка дистрибуции SignFinder для клиентов, которым принципиально важно держать документы и LLM-вызовы внутри собственного периметра.

### 10.1 Бизнес-обоснование

**Целевая аудитория:**
- Корпоративные клиенты с требованиями к конфиденциальности договоров (юридические фирмы, M&A, банки)
- Компании в regulated industries с compliance-требованиями (152-ФЗ для РФ, GDPR для EU)
- Государственные и оборонные структуры, где cloud SaaS запрещён по политикам безопасности
- Компании которые не хотят отпускать договорный документооборот наружу контура

**Что им нужно:**
- Документы никогда не покидают периметр компании
- LLM-вызовы идут с **их** Anthropic API ключа (или другого провайдера в будущем) — они сами контролируют биллинг и privacy с провайдером
- Полная установка в Docker-контейнере на их инфраструктуре
- Интеграция с **их** почтовым сервером (Exchange, Postfix, Zimbra) по IMAP/SMTP
- Без зависимости от нашего облака — мы не получаем ни документов, ни метрик использования

**Модель монетизации:** годовая лицензия (вместо subscription за вызовы API). Цена контракта от $5k до $50k в год в зависимости от объёма обработки.

**Конкуренты:** Adobe Sign On-Premise, KSign, специализированные internal-development решения. У SignFinder уникальное преимущество — фокус именно на **автоматизации поиска мест подписи**, не на полном CLM.

### 10.2 Архитектурное решение: контейнерное приложение на том же ядре

**Не отдельный код, не отдельная команда поддержки.** Тот же `signfinder-core` Python-пакет работает локально в Docker-контейнере на инфраструктуре клиента.

```
signfinder-core (pip-пакет)
   └── используется в:
       ├── signfinder-api (Cloud) — FastAPI + Cloud Run
       └── signfinder-desktop (On-prem) — Docker контейнер
            ├── Локальный веб-UI (Streamlit или FastAPI + минимальный React)
            ├── IMAP-агент (фоновый воркер, монитор почты)
            └── Конфигурация через .env и volume-mount'ы
```

**Что это значит на практике:**
- Один codebase для бизнес-логики
- Один deployment unit (Docker image)
- Разные `entrypoint` и конфигурации для двух режимов работы
- Cloud и Desktop версии обновляются синхронно (новая версия `signfinder-core` → новые образы для обеих веток)

### 10.4 Сценарий работы IMAP-агента — основной use case

```
Фоновый процесс работает 24/7 в контейнере клиента.

1. Каждые N минут (настраивается, default 5 мин):
   IMAP агент → подключается к серверу клиента
   → читает входящие письма в папке Inbox/SignFinder/
   → для каждого письма с PDF-вложением:
   
2. Извлекает PDF из вложения

3. Вызывает signfinder-core.analyze(pdf)
   → результат: traffic_light (green | yellow | red)

4. По светофору раскладывает письмо в одну из папок IMAP:
   
   🟢 Зелёный → 
     - Подписывает локально через signfinder-core.sign()
     - Создаёт ответное письмо с подписанным PDF
     - Перемещает оригинал в Inbox/SignFinder/Signed/
     - Отправляет ответ через SMTP отправителю (опционально)
   
   🟡 Жёлтый →
     - Перемещает в Inbox/SignFinder/RequiresReview/
     - Оператор открывает локальный Web UI, разбирает вручную
     - После ручной обработки — перемещает в Signed/ или Rejected/
   
   🔴 Красный (ошибка обработки) →
     - Перемещает в Inbox/SignFinder/Failed/
     - Логирует причину в JSON-лог
     - Опционально: уведомление администратору
```

**Структура папок в IMAP клиента:**

```
Inbox/
└── SignFinder/
    ├── (incoming)           ← пользователи сюда складывают документы
    ├── Signed/              ← подписанные документы
    ├── RequiresReview/      ← требуют ручной обработки
    ├── Failed/              ← ошибки обработки
    └── Archive/             ← обработанные старше N дней (опционально)
```

### 10.5 Принципы реализации

**Принцип 1: контейнер должен запускаться `docker run` без облачных зависимостей**

```bash
docker run -d \
  -p 8501:8501 \
  -e ANTHROPIC_API_KEY=sk-... \
  -e IMAP_HOST=mail.company.com \
  -e IMAP_USER=signbot@company.com \
  -e IMAP_PASSWORD=secret \
  -e SMTP_HOST=mail.company.com \
  -e SMTP_USER=signbot@company.com \
  -e SMTP_PASSWORD=secret \
  -e STORAGE_MODE=local \
  -v ./signfinder-config:/app/config \
  -v ./signfinder-templates:/app/templates \
  -v ./signfinder-signatures:/app/signatures \
  -v ./signfinder-logs:/app/logs \
  signfinder/desktop:latest
```

Никаких обращений к Google Cloud, AWS, или нашим серверам. Только Anthropic API наружу (с ключом клиента).

**Принцип 2: одинаковая core-логика, разная обвязка**

Cloud-вариант → FastAPI обёртка → доступ извне через HTTPS
Desktop-вариант → Streamlit/локальный UI + IMAP-агент → доступ только внутри контейнера/сети клиента

Бизнес-логика идентична. Различие только в **транспорте** и **точках входа**.

**Принцип 3: storage abstraction уже готова**

Текущий `core/storage.py` имеет switch между GCS и localfilesystem. В v1.9 при выделении в `signfinder-core` эта абстракция переедет в пакет:

```python
# signfinder-core/signfinder/storage.py

class StorageBackend(Protocol):
    def read(self, path: str) -> bytes: ...
    def write(self, path: str, data: bytes) -> None: ...
    def list(self, prefix: str) -> list[str]: ...
    def delete(self, path: str) -> None: ...

class LocalFilesystemStorage(StorageBackend):  # для Desktop on-prem
    ...

class GCSStorage(StorageBackend):              # для Cloud
    ...

# В будущем (по запросу):
class S3Storage(StorageBackend):               # для AWS-клиентов
    ...
class AzureBlobStorage(StorageBackend):        # для Azure-клиентов
    ...
```

**Выбор backend через env var:** `STORAGE_MODE=local|gcs|s3|azure`.

**Принцип 4: LLM API key клиента, не наш**

В Cloud-варианте: ANTHROPIC_API_KEY — наш, хранится в Secret Manager.
В Desktop-варианте: ANTHROPIC_API_KEY — клиента, передаётся при запуске контейнера.

Биллинг LLM-вызовов идёт напрямую от клиента к Anthropic, минуя нас. Мы не видим ни запросов, ни ответов LLM.

**Принцип 5: телеметрия по согласию (opt-in)**

В Desktop-варианте по умолчанию **ничего** не отправляется наружу контура. Опционально — анонимная телеметрия (количество обработанных документов, версия, ошибки) для нашей аналитики качества продукта. Включается флагом `TELEMETRY_ENABLED=true`.

### 10.6 Что доступно в Web UI Desktop-варианта

Локальный веб-интерфейс (Streamlit, потом возможно React) доступен на `http://localhost:8501` или сетевом адресе контейнера в инфраструктуре клиента.

**Покрытие функций:**
- Просмотр и управление шаблонами
- Конфигурация подписанта (компания, ФИО, PNG подписи)
- Управление маркерами подписи и parties.json
- Настройки IMAP-агента (расписание, фильтры писем, обработка ошибок)
- Просмотр истории обработки (что в какую папку попало и почему)
- Ручная обработка документов из папки RequiresReview/
- Настройка светофора и порогов
- Просмотр аудит-логов

По сути — **тот же функционал что в Cloud Streamlit**, плюс конфигурация IMAP-агента.

### 10.7 Roadmap Desktop on-premise

**v1.9 (одновременно с Cloud API):**
- Только **подготовка фундамента**: выделить `signfinder-core` как pip-пакет, проверить что нет GCP-привязки в коде, документировать env vars
- Никакого Desktop UI и IMAP-агента — это v2.x

**v2.0 (после Cloud API в продакшене):**
- Если есть подтверждённый клиент — приоритезируем Desktop ветку выше iOS
- Если нет — продолжаем по плану (iOS первой)

**v2.x (по бизнес-кейсу):**
- Сборка Docker-образа `signfinder/desktop:latest`
- Базовый Streamlit UI без облачных зависимостей
- IMAP-агент (фоновый воркер) с базовой логикой (IMAP IDLE, polling fallback, обработка папок)
- Конфигурация SMTP для отправки ответных писем (опционально)
- Документация по установке для системного администратора
- Поддержка Exchange / Postfix / GSuite (хотя бы один из тестируемых, остальные по запросу)

**Срок реализации Desktop при готовом Cloud API:** 4-8 недель в зависимости от сложности IMAP-интеграции и требований клиента.

### 10.8 Что НЕ делаем в Desktop ветке

- **Не делаем нативное GUI приложение** (Electron, Tauri, Qt). Веб-UI в контейнере — проще, дешевле, кросс-платформенно.
- **Не делаем offline режим без интернета вообще.** LLM-вызовы требуют интернет хотя бы до Anthropic API. Полностью air-gapped окружение — отдельная задача (Llama / Mistral локально с GPU), out of scope MVP.
- **Не делаем auto-update контейнера.** Клиент сам обновляет через `docker pull` по своему расписанию. Auto-update в корпоративной среде — антипаттерн.
- **Не делаем централизованную консоль управления несколькими установками** (для MSP сценария). Если возникнет — отдельный продукт.
- **Не делаем сертификацию (ISO 27001, SOC 2, и т.д.)** на старте. Если корп.клиент требует — по запросу, отдельная задача.

### 10.9 Открытые вопросы по Desktop ветке

| Вопрос | Контекст | Решение |
|--------|---------|---------|
| Какой почтовый сервер первым тестируем? | Exchange, Postfix, GSuite, Zimbra — у разных клиентов разное | По первому реальному клиенту |
| OAuth для GSuite/Exchange vs Basic Auth | Современные почтовые серверы требуют OAuth | Поддерживаем оба, OAuth добавляется по запросу |
| Поддержка S/MIME подписания | Криптографическая подпись писем | Out of scope, простая PNG-подпись на PDF достаточна для большинства |
| Quarantine для подозрительных PDF | Антивирус, безопасность | Полагаемся на security клиента, не дублируем |
| Конфигурация через UI vs только через env vars | UX для администратора | Базовое — env vars, sensitive (IMAP пароль) — env vars, остальное — UI |
| Multi-mailbox в одном контейнере | Несколько подписантов | Out of scope v2.x, отдельный контейнер на подписанта |

### 11.3 v1.9 — API-слой (FastAPI как standalone сервис) (14-21 день)

**Цель:** выделить бизнес-логику в отдельный сервис, доступный по REST/HTTPS. Streamlit становится одним из клиентов. Открывается путь для мобильного приложения, MCP-сервера, сторонних интеграций **и Desktop on-premise варианта** (см. главу 10).

Полное описание архитектуры — в главе 8.

**Реализация в 5 частей:**

#### Часть 1. Выделение `signfinder-core` как pip-пакета (3-5 дней)

Это **новая часть в концепции v1.4** — фундамент для всех последующих веток (Cloud API, Desktop on-prem, MCP-сервер, batch-воркеры).

- Новый репозиторий `signfinder-core`
- Перенос `core/*.py` из Streamlit-репо в пакет
- Структура пакета:
  ```
  signfinder-core/
  ├── pyproject.toml
  ├── signfinder/
  │   ├── __init__.py
  │   ├── pipeline.py          # PipelineAuto1
  │   ├── anchors/             # anchor_builder, finder
  │   ├── fingerprint.py
  │   ├── templates/           # template_storage, template_matcher
  │   ├── traffic_light.py
  │   ├── storage/             # abstraction + backends (local, gcs, s3)
  │   ├── llm/                 # Anthropic client wrapper
  │   ├── pdf/                 # parser, overlay, preview
  │   └── config.py            # env vars handling
  ```

- **Storage abstraction:** `LocalFilesystemStorage`, `GCSStorage` (S3 в будущем)

- Документация по использованию пакета:

  ```python
  from signfinder import SignFinder
  ```

**Эффект:** один package с бизнес-логикой, переиспользуется во всех клиентах SignFinder. Готовность к Cloud, Desktop, MCP без дублирования кода.

### 11.4 v1.10 — Мульти-LLM backend (10-14 дней)

**Цель:** ввести возможность выбора LLM провайдера на уровне backend конфигурации. Возможные провайдеры: Anthropic Claude (текущий), OpenAI GPT, DeepSeek. Ручное A/B сравнение качества и стоимости на одном MVP.

**Архитектурный подход:** единый пайплайн обработки, единый набор шагов (extraction, regex generation, validation), но **разные коннекторы** к LLM. Промпты адаптированы под каждого провайдера (формат JSON output, особенности структурирования инструкций), пайплайн остаётся общим.

**Реализация:**

| Что | Детали |
|-----|--------|
| `signfinder-core/llm/base.py` | НОВЫЙ — абстрактный класс `LLMClient` с методом `complete(system, user, expected_json_schema)` |
| `signfinder-core/llm/anthropic_client.py` | Перенос текущей логики Claude в реализацию `LLMClient` |
| `signfinder-core/llm/openai_client.py` | НОВЫЙ — реализация для OpenAI (function calling для JSON) |
| `signfinder-core/llm/deepseek_client.py` | НОВЫЙ — реализация для DeepSeek (response_format для JSON) |
| `signfinder-core/llm/prompts/` | НОВАЯ структура — папка с промптами per provider: `anthropic/*.txt`, `openai/*.txt`, `deepseek/*.txt`. Каждый промпт адаптирован под особенности провайдера |
| Конфигурация | `LLM_PROVIDER=anthropic|openai|deepseek` env var, `<PROVIDER>_API_KEY` для ключа |
| Streamlit UI | Селектор провайдера в админке (или env только) для переключения на лету при тестировании |
| Логирование | Каждый LLM-вызов помечается провайдером в логе для аналитики |

**Цель тестирования:**
- Какой провайдер даёт лучшее качество на нашем формате договоров (RU/EN/PL)
- Какая стоимость за обработку одного документа
- Какая скорость отклика
- Какое поведение на edge cases (длинные документы, нестандартные формулировки)

**Сравнение делается вручную** оператором — без автоматических метрик precision/recall. Это сознательный выбор для MVP — автометрика дорогая, ручной анализ на 30-50 документах достаточен для решения.

**Что НЕ в v1.10:**
- Автоматический выбор LLM на основе типа документа (на v1.10 пользователь выбирает один)
- Per-tenant выбор LLM (это в multi-tenant ветке развития, глава 15)
- Fallback между провайдерами (если Anthropic не отвечает — switch на OpenAI). Это потенциально полезно, но добавляется только если возникнет реальная необходимость
- Параллельное A/B (один документ обрабатывается двумя LLM одновременно для сравнения). Out of scope MVP — это уже промышленный testing framework

**Сроки и риски:**
- 10-14 дней включает адаптацию промптов под каждого провайдера (это самая трудоёмкая часть)
- Риск: качество OpenAI или DeepSeek может оказаться существенно ниже Claude на русском языке. Если так — фиксируем это в результатах тестирования и продолжаем на Claude как primary

### 11.5 v1.11 — IMAP-клиент в Docker (single-user, on-premise) (4-6 недель)

**Цель:** standalone Docker-контейнер для корпоративных клиентов, которые не хотят отправлять договоры в облако. Один контейнер = один подписант (single-user). Документы обрабатываются локально, LLM-вызовы идут с **их** API-ключом.

Полное описание архитектуры — в главе 10.

**Изменения по сравнению с концепцией v1.4:**
- Раньше это была v2.2 как «Desktop on-premise ветка». Теперь поднято в v1.11 — становится приоритетом ради конкретного корп.клиента
- Упрощено до **single-user** (один подписант, один контейнер) — multi-mailbox/multi-signer вынесены в идеи развития
- Не требует multi-tenant инфраструктуры — каждая инсталляция автономна

**Реализация:**

| Часть | Что | Срок |
|-------|-----|------|
| 1. Финализация `signfinder-core` как pip-пакета | Проверка отсутствия GCP-зависимостей кроме `storage/gcs.py`. Полная документация env vars. Storage abstraction поддерживает local filesystem | 3-5 дней (в основном уже сделано в v1.9 Часть 1) |
| 2. Docker image `signfinder/desktop:latest` | Базовый Streamlit UI + IMAP-агент + LLM client (по выбору из v1.10) на одном образе | 1 неделя |
| 3. IMAP-агент | Фоновый процесс. IMAP IDLE + polling fallback. Мониторинг папки `Inbox/SignFinder/`. Защита от повторной обработки одного письма | 1-1.5 недели |
| 4. Логика раскладки по светофору | Зелёный → подпись и `Signed/`. Жёлтый → `RequiresReview/`. Ошибка → `Failed/`. Опционально: SMTP отправка ответных писем | 1 неделя |
| 5. Документация для администратора | Установка, конфигурация env vars, troubleshooting, описание формата папок IMAP | 3-5 дней |
| 6. Тестирование на конкретном почтовом сервере клиента | Exchange / Postfix / GSuite — по реальному клиенту. Поддержка остальных серверов — по запросу позже | 5-7 дней |

**Конфигурация:**

```bash
docker run -d \
  -p 8501:8501 \
  -e LLM_PROVIDER=anthropic \
  -e ANTHROPIC_API_KEY=sk-... \

  -e IMAP_USER=signbot@company.com \
  -e IMAP_PASSWORD=secret \
  -e SMTP_HOST=mail.company.com \
  -e STORAGE_MODE=local \
  -v ./config:/app/config \
  -v ./templates:/app/templates \
  -v ./signatures:/app/signatures \
  -v ./logs:/app/logs \
  signfinder/desktop:latest
```

**Структура папок в IMAP клиента:**

```
Inbox/
└── SignFinder/
    ├── (incoming)           ← пользователи кладут документы для обработки
    ├── Signed/              ← подписанные документы (зелёный светофор)
    ├── RequiresReview/      ← жёлтый светофор, ручной разбор оператором
    ├── Failed/              ← ошибки обработки
    └── Archive/             ← обработанные старше N дней (опционально)
```

**Бизнес-обоснование:**
- Корп.клиенты с требованиями к конфиденциальности договоров
- Compliance: 152-ФЗ, GDPR, отраслевые требования банков и юрфирм
- Модель монетизации: годовая лицензия $5k-50k
- Клиент сам платит за LLM-вызовы (свой API-ключ)
- Не требует подключения к нашему облаку

**Что НЕ в v1.11:**
- Multi-mailbox в одном контейнере (один подписант)
- Параллельная обработка нескольких потоков (последовательная обработка достаточна для начала)
- Сертификация ISO 27001 / SOC 2 (по запросу клиента, отдельная задача)
- S/MIME подписание писем (PNG-подпись на PDF достаточна)
- Auto-update контейнера (клиент сам обновляет через `docker pull`)
- Кросс-платформенные нативные приложения (Windows GUI, macOS .app — это уже не MVP)

### 11.6 v1.12 — Pre-flight check (правила целостности договора, 14-21 день)

**Цель:** перед автоматическим подписанием проверять что договор юридически целостный. Это **второй светофор** (целостности), отличный от светофора шаблонов (узнавания).

**Это финальная версия MVP.** После v1.12 цикл разработки MVP логически завершён — продукт умеет: автоматически подписывать типовые договоры, узнавать похожие документы, проверять целостность перед подписанием, работать через API, работать в Docker on-premise, использовать разных LLM провайдеров.

**Реализация:**

| Что | Детали |
|-----|--------|
| `signfinder-core/playbook/rules.py` | Правила R-01..R-07 (см. ниже) |
| `signfinder-core/playbook/extractor.py` | Извлечение сущностей (стороны, подписанты, юрлица) через LLM provider из v1.10 |

| Drill-down по правилам | Какое правило провалилось и почему |
| Аудит-лог решений | Структурированный JSONL для юридической защиты |
| `verification_rules.json` | Конфигурация порогов правил, редактируется через UI |

**Правила pre-flight check:**

| ID | Правило | Уровень при провале |
|----|---------|----------------------|
| R-01 | Каждая сторона из шапки имеет ≥1 место подписи | 🔴 красный |
| R-02 | Места подписи симметричны по сторонам | 🟡 жёлтый |
| R-03 | Маркер у места подписи соответствует синониму стороны | 🟡 жёлтый |
| R-04 | Места подписи пустые (нет уже наложенной подписи) | 🟡 жёлтый |
| R-05 | Сторона нашего подписанта определена однозначно | 🔴 красный |
| R-06 | В местах подписи нет конфликтующих ФИО | 🟡 жёлтый |
| R-07 | Каждый раздел/приложение завершается местами подписи | 🟡 жёлтый |

**Что НЕ в скоупе v1.12:**
- Полный юридический анализ договора (риски, противоречия, соответствие законодательству)
- Детекция уже наложенной подписи второй стороны (детекция кистевой подписи как изображения)
- Анализ соответствия договора корпоративным политикам
- Машинное обучение правил на основе исторических ошибок оператора

## 12. Технологические решения для запоминания

### 12.1 Уровни обработки и стоимость

Базовый принцип: **самый дешёвый метод первым, самый дорогой последним**. Большинство документов закрывается regex+LLM-валидацией. LLM-fallback и ручная разметка — для меньшинства.

### 12.2 Облачные сервисы парсинга

**В концепции v1.3 — все облачные сервисы парсинга отложены за v2.0** как преждевременная оптимизация для мидл-сегмента 10-страничных договоров. Краткий обзор сохраняется в концепции на случай если в будущем потребуется:

- **Google Document AI** — кандидат когда понадобится OCR для сканированных PDF или batch-обработка 1000+ документов/мес
- **AWS Textract** — резерв для табличных кейсов и (опционально) детекции подписей второй стороны
- **Azure Form Recognizer** — не нужен на GCP-стеке

Подробное сравнение сервисов сохранено в главе 4.2 для исторической справки и быстрого возврата к вопросу при необходимости.

### 12.3 Шаблоны документов

- **SimHash** для fingerprint на v1.4.3 — простой и быстрый алгоритм
- **Embeddings (sentence-transformers, Voyage, OpenAI ada)** — рассмотреть на v3.0, когда библиотека шаблонов вырастет до 100+
- Шаблон хранится отдельно от parties.json — это разные сущности

### 12.4 Тестирование и метрики

- На v1.3-v1.4 — глазами, формат таблицы + JSON-экспорт для дебага
- На v1.5 — простая агрегация прогонов
- На v2.0+ — автометрика precision/recall на размеченной выборке

### 12.5 LLM-провайдер

**В концепции v1.5 решение по LLM-абстракции пересмотрено относительно v1.3:**

- **До v1.10:** Claude Sonnet 4.6 — единственный провайдер. На 10-страничных договорах MVP — $0.01-0.03 на документ
- **В v1.10:** Вводится **LLMClient abstraction** с поддержкой Anthropic, OpenAI, DeepSeek. Цель — ручное A/B сравнение качества и стоимости. Пользователь выбирает одного провайдера, на нём гоняются все промпты. Промпты адаптированы под каждого провайдера, но пайплайн один
- **После v1.10:** На основе результатов сравнения выбирается primary провайдер. Остальные остаются доступными для переключения через конфигурацию
- **Gemini** — потенциальный кандидат для добавления в LLMClient в будущем (за пределами MVP). Активируется при появлении экономической потребности
- **Локальные модели (Llama, Mistral)** — out of scope MVP, требуют GPU и сложной инфраструктуры

**Принципиальный архитектурный момент:** в v1.10 промпты живут **per provider** в отдельных папках (`prompts/anthropic/`, `prompts/openai/`, `prompts/deepseek/`). Это потому что качественный JSON output у каждого провайдера достигается разным способом, и промпты не one-size-fits-all.

## 15. Идеи развития (после завершения MVP)

Эта глава появилась в концепции v1.5. После завершения MVP на v1.12 продукт логически готов как «утилита подписания» — Streamlit, API, Docker on-premise, разные LLM, проверка целостности.

**Следующий цикл развития** — превращение в полноценный SaaS-продукт с многопользовательским режимом, биллингом, личными кабинетами и мобильными клиентами. Это переход в другую бизнес-модель и другой объём работы.

**Этот цикл не входит в MVP.** Здесь собраны идеи и направления для следующего этапа продукта, чтобы зафиксировать архитектурное видение и приоритизацию.

### 15.1 Multi-tenant SaaS — основа следующего цикла

**Цель:** превратить SignFinder из single-tenant утилиты в многопользовательскую SaaS платформу.

**Что нужно сделать:**

| Компонент | Описание |
|-----------|----------|
| Концепция tenant | Tenant = клиент (компания или индивидуальный пользователь). Tenant имеет: пользователей, шаблоны, конфигурации, API-ключи, лимиты использования |
| Tenant-isolation | Логическая изоляция данных: один GCS bucket с префиксами `tenants/{tenant_id}/...`. Файловые системы, конфиги, шаблоны — per-tenant |
| Per-tenant API keys | Ключи привязаны к tenant_id. Имеют TTL и лимиты на количество вызовов или токенов |
| Внутренний биллинг-счётчик | Каждый LLM-вызов считается в токенах per-tenant. Используется для расчёта подписки |
| Per-tenant промпты | Базовые промпты копируются с глобальной библиотеки, могут редактироваться внутри tenant. Изолированы от других tenants |
| Per-tenant шаблоны | Аналогично — клиент видит и редактирует только свои шаблоны |
| Per-tenant выбор LLM | Каждый клиент сам выбирает провайдера (Anthropic / OpenAI / DeepSeek) |
| Admin console | Отдельный интерфейс для администрирования tenants (создание, ключи, лимиты, аналитика) |

**Срок реализации:** 8-12 недель чистой работы. Требует фундаментального рефакторинга storage abstraction, добавления tenant_id во все операции, проектирования admin-консоли.

**Триггер активации:** подтверждённый план product-led growth, готовая команда поддержки, бюджет на маркетинг.

### 15.2 Пользовательский сайт с регистрацией

**Цель:** self-service onboarding для конечных пользователей.

**Что нужно:**
- Регистрация с email-подтверждением (SendGrid, Mailgun, AWS SES — на выбор)
- Личный кабинет пользователя: профиль, подпись, реквизиты компании
- Админка шаблонов: список с метаданными (имя, дата создания, количество применений, среднее время обработки)
- Админка сторон (parties.json в UI вместо ручного редактирования JSON)
- Админка LLM backend (выбор провайдера, ввод своего API-ключа если разрешено)
- Просмотр аудит-лога обработанных документов
- Биллинговая интеграция (Stripe / ChargeBee для подписок)
- Восстановление пароля
- ToS / Privacy Policy / GDPR compliance

**Срок реализации:** 12-16 недель. Это **самостоятельный продукт** — отдельный web-фронтенд (React/Vue), отдельная команда фронтенд-разработки.

**Триггер активации:** активация v1.10 multi-tenant + готовность к платежам.

### 15.3 Мобильные клиенты (iOS, Android)

**Цель:** нативные мобильные приложения для подписания на ходу.

**Что планировалось в концепции v1.4:**
- iOS первой платформой (см. главу 9)
- Android после фидбека от iOS
- Основной flow «получил договор по почте → подписал на ходу»
- Управление шаблонами, обновление подписи через камеру

**Архитектура:** SwiftUI + URLSession для iOS, Kotlin/Compose для Android. Полное описание архитектуры — в главе 9 концепции (сохранена как архитектурный референс).

**Срок реализации:** iOS — 6-8 недель, Android — 5-7 недель.

**Триггер активации:** запросы от пользователей сайта о возможности работать с телефона. Без подтверждённого спроса — не делаем.

### 15.4 Sessions для двустороннего подписания

**Цель:** подписать → отправить контрагенту по ссылке → контрагент подписывает → готовый документ обеим сторонам.

**Что нужно:**
- Новая сущность SigningSession с TTL 7 дней
- Endpoints `/v1/sessions/*` для создания, подписания, получения результата
- Магическая ссылка (или код по SMS) для подписи контрагентом
- Storage документов на сервере на время сессии (нарушает stateless архитектуру)
- UI для отправки на подпись из мобильного приложения и сайта

**Срок реализации:** 2-3 недели.

**Триггер активации:** запросы от пользователей мобильного приложения или сайта о двустороннем подписании.

### 15.5 Расширенные LLM-возможности

**За пределами v1.10 мульти-LLM:**

| Фича | Описание |
|------|----------|
| Автоматический fallback между провайдерами | Если основной не отвечает — переключение на резервный |
| Параллельное A/B на одном документе | Два провайдера обрабатывают одновременно, сравниваем результаты в реальном времени |
| Per-task choice of LLM | На extraction — Claude (качество), на простую валидацию — DeepSeek (дешёво) |
| Локальные LLM (Llama, Mistral) | Для air-gapped окружений или экономии. Требует GPU |
| Google Document AI Contract Parser | Альтернатива LLM extraction. Возможен при необходимости обрабатывать сканы или batch 1000+ док/мес |
| Кастомные fine-tuned модели | На корпусе договоров клиента — может появиться для крупных корп.клиентов |

### 15.6 MCP-сервер для интеграции с Claude Desktop / Cursor

**Цель:** позволить разработчикам и юристам использовать SignFinder из Claude Desktop, Cursor, других AI-IDE через MCP протокол.

**Реализация:**
- Тонкий MCP-сервер поверх готового API (1-2 недели работы)
- Tools: `analyze_pdf`, `list_templates`, `sign_with_template`, `manage_signers`
- Авторизация через API key из конфига MCP

**Срок реализации:** 1-2 недели после v1.9 API.

**Триггер активации:** запросы от разработчиков использующих эти инструменты.

### 15.7 Расширенный конвейер (bulk + ретенция)

**Что было в концепции v1.4 как v1.10 «Конвейер»**, теперь — идея развития:

- Bulk-загрузка нескольких документов в одну сессию через drag&drop
- Сводная таблица: документ → светофор → шаблон → действия
- Drill-down с деталями fingerprint, score breakdown, найденных мест
- Ретенция шаблонов (cron + retention.py): архивация неиспользуемых через 30 дней, удаление через 90
- Logger в JSONL для аналитики

**Срок реализации:** 10-14 дней.

**Триггер активации:** появление потока документов >50/день у одного пользователя.

### 15.8 RBAC, Multi-mailbox, Enterprise features

**Для крупных корп.клиентов:**

| Фича | Описание |
|------|----------|
| RBAC | Несколько ролей внутри одного tenant (admin, signer, viewer) |
| Multi-mailbox в Docker IMAP | Несколько подписантов в одном контейнере (расширение v1.11) |
| SAML / OIDC SSO | Корпоративная аутентификация через identity provider клиента |
| Audit log API | Программный доступ к журналу для интеграции с SIEM-системами |
| Compliance reports | Готовые отчёты для аудита (152-ФЗ, GDPR, SOC 2) |
| Сертификации (ISO 27001, SOC 2) | По запросу крупных клиентов, отдельная задача |

**Срок реализации:** каждая фича 1-4 недели. Делаются реактивно по запросу клиентов.

### 15.9 Принципы приоритизации идей развития

Все идеи в этой главе — **реактивные**, не проактивные. Вводим когда:

1. Есть подтверждённый бизнес-кейс — конкретный клиент готовый платить
2. Есть достаточно ресурсов разработки — не за счёт критичных задач MVP
3. Архитектурно нет долга — текущая версия стабильна

**Самые вероятные ближайшие шаги после MVP:**

1. Multi-tenant + сайт регистрации (если планируется product-led growth)
2. MCP-сервер (быстро, дёшево, расширяет круг пользователей)
3. iOS приложение (если есть пользователи запрашивающие мобайл)
4. Sessions (если есть запрос на двустороннее подписание)

**Что не делаем превентивно:**
- Полная сертификация (ISO 27001, SOC 2) — дорого, без конкретного клиента бесполезно
- Локальные LLM — требует GPU и сложной инфраструктуры, без явной экономической потребности
- Custom fine-tuned модели — преждевременная оптимизация для MVP-стадии
